## 任务契约

- **任务名称：** SM120 上的 BF16 Tensor Core Attention Decode。
- **目标硬件：** 当前机器实际安装、可运行 `sm_120` 代码的 NVIDIA GPU。先记录 GPU 型号、计算能力、驱动、CUDA 工具链以及所选框架版本；若硬件或工具链不匹配，报告阻碍并保留可在目标机器执行的代码与命令，不要伪造性能结果。当前是5060的笔记本，在wsl环境下。
- **辅助 Skill 的使用边界：** 可以使用 `$KernelWiki` 检索内核优化思路和上游实现，也可以使用 `$ncu-report-skill` 组织 Nsight Compute 的采集、诊断与报告流程。但本任务的目标架构是 `sm_120`；`KernelWiki` 的知识主体面向 Hopper `sm_90` 和数据中心 Blackwell `sm_100`，`ncu-report-skill` 则明确以 B200/`sm_100` 为目标，因此只能借鉴其中与架构无关的方法和候选思路，不能直接照搬架构结论。凡涉及指令可用性、Tensor Core 形状、TMEM/CLC/tcgen05 等硬件特性、资源上限、调度策略、NCU 指标名称或性能参数的内容，都必须通过 `sm_120` 官方资料、实际编译产物/SASS、目标 GPU 上的运行结果和 profiler 数据重新核验；最终判断以本机 `sm_120` 证据为准。
- **计算语义：** 单步 decode，query 长度固定为 1。输入 `Q: [B, Hq, 1, D]`、`K/V: [B, Hkv, T, D]`，均为连续内存布局和 BF16；输出 `O: [B, Hq, 1, D]`，为 BF16。要求 `Hq % Hkv == 0`，采用 GQA 头映射 `kv_head = q_head // (Hq / Hkv)`。计算 `softmax(QKᵀ / sqrt(D))V`，注意力范围覆盖提供的全部 `T` 个 token，不另加 mask 或位置偏置。Softmax 的最大值、分母和输出归约使用 FP32；处理长序列时保持数值稳定。
- **首版工作负载：** `B ∈ {1, 4}`，`(Hq, Hkv) ∈ {(32, 8), (32, 32)}`，`D ∈ {64, 128}`，`T ∈ {1, 127, 128, 129, 512, 2048, 8192}`。所有组合都需正确；性能统计以 `T ≥ 128` 的组合为主，同时报告 `T=1` 和非整齐边界的延迟。若显存不足，记录无法运行的组合及原因，不静默删去。
- **实现方式：** 只能使用 CUDA C++实现 GPU 内核，tirton，cute，cutlass，dsl都不可以，并提供 Python 调用入口。主要矩阵运算路径必须实际使用 BF16 Tensor Core 指令；不得仅以源码中出现相关 API 作为证明。允许针对短序列或退化形状增加分派路径，但必须记录每个路径的适用范围，并保证整个任务契约的正确性。不得更改测试数据或评估逻辑来获取收益。
- **正确性要求：** 用 PyTorch FP32 参考计算生成结果，再转换为 BF16 进行比较；默认逐元素容差 `atol=2e-2, rtol=2e-2`，另记录最大绝对误差和最大相对误差。若该容差与参考计算的舍入行为冲突，应在实现前用基线实验说明并固定新标准，不得为了让候选方案通过而事后放宽。检查输出形状、dtype、有限值、全部规定组合及边界长度。
- **性能目标：** 在同一设备和运行环境下，以 PyTorch `scaled_dot_product_attention` 的等价调用和我conda 环境下llm-bench的fa2作为基线，比较端到端调用延迟；记录每个形状的中位数、重复测量波动和 `T ≥ 128` 用例的几何平均加速比。我的目标是继续逼近这台机器上、既定接口和数值约束下的性能上限。不要因为已经超过 SDPA / FA2，就结束优化。你需要修改实现、做真实实验，并用证据解释还能快在哪里、为什么某条路线无效，以及最终距离可解释的性能下界还有多远。同时，你可以参考flash attn3，flash attn4,/home/user/cqupt/ai_infra/flashinfer和/home/user/cqupt/ai_infra/nv_hpc_ops/hgemm/csrc/hgemm进行相关的参考，涉及相关的流水和使用sm120特殊有的tma。有三个阶段性的目标，要求加速比达到2倍，达到3倍和5倍。
- **验证命令：** `python -m pytest -q tests/test_attention_decode.py`。建立测试后，确保该命令覆盖任务契约；如实际环境需要额外构建步骤或参数，将完整可复现命令写入 `docs/plan.md`。
- **评估命令：** `python benchmarks/bench_attention_decode.py --output benchmark.csv`。基准脚本须包含预热、重复测量、设备同步与统一的计时口径，并输出设备信息和逐形状结果。若脚本接口因实现技术变化，更新此提示词及计划中的命令后再评估。
- **晋级标准：** 全部可运行的规定用例通过正确性检查；Tensor Core 路径有可复核的编译产物或 profiler 证据；相同条件下重复评估，收益超过测量波动且整体性能无明显回退；候选方案、父方案、验证、评估和取舍原因均有记录。达到性能目标时可作为最终候选；未达到时如实提交最佳正确实现及瓶颈证据。

## 工作流

1. 检查工作区、设备和工具链，确认选用的实现技术在实际目标设备上可用。
2. 建立 FP32 参考实现、等价 PyTorch 基线、覆盖完整工作负载的测试和统一基准。固定比较容差与计时方法，记录基线正确性及性能。
3. 只研究解决当前实现问题所需的硬件、指令、库 API 和已有实现；核实 Tensor Core 指令及编译目标的实际支持情况。
4. 将基线、风险、候选方向、首批步骤、精确命令和晋级证据写入 `docs/draft.md`；再整理为 `docs/plan.md`。完成这两步前不要编辑内核实现。
5. 每次只实现一个候选方案。重点分析单 token query 的矩阵形状、KV 读取量、Tensor Core 利用率、在线 softmax、长序列归约和短序列启动开销；通过测量决定是否分派。
6. 每次修改后先运行正确性验证，再运行评估。把候选名称、父方案、修改摘要、验证结果、逐形状延迟和晋级决定写入 `candidates.jsonl`、`benchmark.csv`；将必要的运行输出和 profiler 证据存入 `runs/`、`outputs/`、`profile/`。
7. 最终复跑完整验证与评估，给出实际设备、最终结果、未覆盖情形和仍存在的性能瓶颈。

### 1\. 从 draft 生成 plan

```
$humanize-gen-plan --input docs/draft.md --output docs/plan.md
```

Humanize 会检查草稿是否存在、是否为空，以及是否与当前仓库相关；再检查目标、约束、步骤和指标是否清楚。发现信息缺失或指标含义不明时，它会先请你澄清，然后生成结构化计划，通常包括：

- 目标和验收条件（`AC-1`、`AC-2` 等）
- 改动范围和允许使用的技术
- 实施步骤、依赖和里程碑
- 验收所需的验证方式

对 5060 HGEMM 来说，计划应把 GPU 型号、矩阵形状、数值容差、基线和评测命令写清楚。此步骤只生成计划，不开始实现。

注意：`docs/` 目录要先存在，而且 `docs/plan.md` 不能已经存在；若已有计划，换一个输出文件名，例如 `docs/plan-v2.md`。

### 2\. 启动 RLCR 实现循环

确认计划后调用：

```
$humanize-rlcr docs/plan.md --max 12
```

这一步才开始按计划改代码。每轮会读取任务提示、实现变更、按计划进行验证、提交本轮变更并生成摘要；Humanize 的 Stop hook 随后触发 Codex review。发现问题就进入下一轮，直到完成或达到 12 轮上限；默认上限是 42 轮。

RLCR 是执行循环，不是测试器：正确性和性能测试要在 plan 中写明并由执行过程运行。开始前先检查计划和 Git 工作区状态，因为循环会产生本地提交。
